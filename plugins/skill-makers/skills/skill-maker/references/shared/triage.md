# 범위 계약과 리뷰 항목 판정

수렴리뷰와 교차 검증에서 나온 모든 항목에 같은 판정을 적용한다.
리뷰어나 상대 AI의 지적을 그대로 반영하지 않는다. 작성자가 타당성을 판단한 뒤 반영한다.

## 1. 범위 계약

plans 단계에서 확정하고 이후 모든 단계의 불변값으로 삼는다.

| 구획 | 내용 | 이후 효력 |
|---|---|---|
| 포함 | 이번 작업이 만들거나 바꾸는 것 | spec·impl_plans·최종 산출물의 상한 |
| 변경하지 않음 | 논의됐지만 하지 않기로 한 것과 인접 영역 | 리뷰가 되살리지 못한다 |

범위 계약을 바꾸는 경로는 둘뿐이다. 사용자 지시, 그리고 §3의 안전 결함을 반영하느라 범위가 달라지는 경우다.
둘 다 plans 헤더의 리뷰 기록에 "범위 계약 개정: 사유"로 남긴다.

## 2. 판정 순서

항목마다 차례로 묻는다.

1. **사실 오류·모순·실행 불가인가?** (경로·값·명령·이름·순서가 틀렸거나 서로 어긋난다)
   → **문서 결함**. 반영한다.
2. **§3의 안전 결함인가?** → **문서 결함(안전)**. 반영한다. 반영으로 범위 계약이 달라지면 개정을 기록한다.
3. **이 항목이 없으면 plans의 완료 기준 중 어느 것이 실패하는가?** 특정할 수 있으면
   → **문서 결함(누락)**. 반영한다.
4. 어느 것도 아니면 → **확장 제안**(구조 개선·추가 검증·미래 대비·취향). 반영하지 않고 `backlog.md`에 등재한다.

지적이 사실과 다르면(리뷰어의 오독) 반영하지 않고, 리뷰 기록에 기각 사유를 한 줄 남긴다.

리뷰어가 severity를 높게 매겼어도 1~3번에 해당하지 않으면 확장 제안이다.
severity는 문서 결함의 긴급도이지 범위를 넓히는 근거가 아니다.
검증 단계도 같다. 완료 기준에 대응하지 않는 검증·시나리오는 확장 제안이다.

## 3. 안전 결함

완료 기준에 적혀 있지 않아도 문서 결함으로 다룬다. 다음 중 하나에 해당하고, 일어나는 경위를
한 문장(누가·무엇을 하면·무엇이 망가지는가)으로 쓸 수 있어야 한다.

- 산출물을 그대로 수행하면 데이터가 손상·유실되거나 복구할 수 없는 상태가 된다.
- 비밀값·개인정보가 노출된다.
- 권한 없는 접근이나 승인되지 않은 외부 효과(배포·발송·결제 등)가 일어난다.

경위를 한 문장으로 쓸 수 없으면 안전 결함이 아니다. §2의 3번부터 이어서 판정한다.

## 4. backlog.md

`.makers/<종류>/<이름>/backlog.md`. 항목이 0이면 만들지 않는다.
plans·spec·impl_plans·최종 산출물은 이 파일을 참조하지 않는다.

```markdown
# backlog — <이름>

| ID | 출처 | 내용 | 미포함 사유 | 후속 조건 |
|---|---|---|---|---|
| B-01 | plans R1 최소성 | … | 확장 제안(§2-4) | … |
```

- 출처: `<단계> R<라운드> <관점>`. 교차 검증이면 `cross R<라운드>`.
- 미포함 사유: §2의 판정 번호를 인용한다.

## 5. 자주 나오는 합리화

| 생각 | 실제 |
|---|---|
| "이왕 손대는 김에 주변도 정리하자" | 범위 계약 밖이다. backlog. |
| "리뷰어가 HIGH로 냈으니 반영해야 한다" | §2의 1~3번에 해당하지 않으면 확장 제안이다. |
| "상대 AI가 지적했으니 맞을 것이다" | 상대의 지적도 같은 판정을 거친다. |
| "검증은 많을수록 좋다" | 완료 기준에 대응하지 않는 검증은 확장 제안이다. |
| "새로 만드는 게 더 깔끔하다" | 깔끔함은 근거가 아니다. 이미 있는 것으로 되면 그것을 쓴다. |
| "차단급이 남았으니 한 라운드 더" | 줄지 않으면 유형부터 센다. 과반 유형은 구조 결함이다. |
