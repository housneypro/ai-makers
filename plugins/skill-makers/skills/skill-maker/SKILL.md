# skill-maker

만들 스킬에 대한 요구를 받아 **순차 정제**한 뒤 스킬 디렉터리를 생성한다.

```
조사 → plans ─(수렴리뷰)→ spec ─(수렴리뷰)→ impl_plans ─(수렴리뷰)→ 스킬 생성 → 교차 검증·수정 → 확정
```

최종 목표는 이 대화를 모르는 에이전트가 스킬 디렉터리만 받아, 필요한 때에 스스로 로드하고 끝까지 따를 수 있는 상태다.

## 먼저 읽을 문서

| 문서 | 언제 |
|---|---|
| [references/skill-format.md](references/skill-format.md) | plans 작성 전. 스킬의 형식과 단계별 문서의 필수 절 |
| [references/shared/artifact-layout.md](references/shared/artifact-layout.md) | 시작할 때. 디렉터리 구조·번호·헤더·독립성 |
| [references/shared/convergence-review.md](references/shared/convergence-review.md) | 첫 수렴리뷰 전. 리뷰어·관점·라운드 상한 |
| [references/shared/triage.md](references/shared/triage.md) | 리뷰 항목을 종합하기 전. 범위 계약과 판정 |
| [references/shared/cross-verification.md](references/shared/cross-verification.md) | 교차 검증 전 |

## 원칙

- **필요가 먼저다.** 스킬이 해결할 반복 문제와, 스킬이 없을 때 에이전트가 실제로 틀리는 지점을 확인한 뒤에 쓴다.
- **순차 생성.** 각 단계는 이전 단계 산출물을 근거로만 쓰고, 수렴해야 다음 단계로 간다.
- **범위 계약은 불변이다.** 스킬이 하는 일과 하지 않는 일을 plans에서 확정하고 이후에 넓히지 않는다.
- **스킬은 호스트 중립적으로 쓴다.** 특정 호스트의 도구 이름 대신 행위("파일을 읽는다", "명령을 실행한다")로 적는다.
  사용자가 한 호스트 전용 스킬을 명시적으로 원하면 그 호스트를 전제 조건으로 스킬에 적는다.
- **스킬은 짧게.** 본문은 절차와 판단 기준만 두고, 상세는 스킬 안의 `references/`로 분리한다.
- **사용자가 멈추라고 하면 멈춘다.** 재개하면 그 단계의 수렴리뷰부터 잇는다.

## 절차

### 0. 스코프 확정

- `<이름>`(소문자·숫자·하이픈)과 스킬의 용도 한 줄을 정한다.
- **출력 위치**를 정한다. 호출할 때 받았으면 그곳이다. 받지 않았으면 현재 프로젝트에서
  호스트가 프로젝트 스킬을 읽는 위치를 제안하고 사용자에게 확인한다. 스킬은 `<출력 위치>/<이름>/`에 생성한다.
- 용도·사용 상황·기대 결과가 논의로 정해지지 않았으면 여기서 멈추고 사용자와 먼저 정한다.
- `.makers/skill/<이름>/`을 현재 작업 디렉터리에 만든다.

### 1. 조사

- 같은 일을 하는 스킬이 이미 있는지 찾는다(현재 호스트에 설치된 스킬, 출력 위치의 기존 스킬).
  있으면 사용자에게 알리고 새로 만들지, 기존 것을 쓸지 정한다.
- 스킬이 다룰 작업을 실제로 어떻게 하는지 확인한다. 필요한 명령·파일·외부 도구가 실제로 있는지 본다.
- 스킬이 로드돼야 하는 사용자 발화 예시와, 로드되면 안 되는 비슷한 발화 예시를 모은다.

### 2. plans

`plans/00-<이름>-plan.md`를 skill-format §2의 필수 절로 쓴다. 범위 계약을 여기서 확정한다.
수렴리뷰 관점: 정합성·최소성·완결성.

### 3. spec

`spec/01-<이름>.md`에 스킬의 설계를 확정한다(skill-format §3). description 문구, 절차, 파일 구성을 정한다.
수렴리뷰 관점: 정합성·최소성·완결성.

### 4. impl_plans

`impl_plans/01-<이름>.md`에 스킬의 모든 파일을 전문으로 쓴다(skill-format §4).
수렴리뷰 관점: 정합성·최소성·완결성·구현가능성.

### 5. 스킬 생성

impl_plans의 파일 전문을 `<출력 위치>/<이름>/`에 그대로 만든다. 스크립트가 있으면 한 번 실행해 동작을 확인한다.

생성 후 독립성 관점으로 스킬 디렉터리를 리뷰하고, artifact-layout §4의 기계 검사를 통과시킨다.
이어서 skill-format §5의 시나리오 확인을 수행한다.

### 6. 교차 검증

cross-verification.md를 따른다. 대상은 생성된 스킬 디렉터리뿐이다.
조건을 충족하지 못하면 건너뛰고 기록한다.
반영할 때는 impl_plans와 생성된 스킬을 함께 고쳐 둘이 어긋나지 않게 하고, 기계 검사를 다시 통과시킨다.

### 7. 마무리

사용자에게 다음을 보고한다.

- 스킬 위치와 파일 목록, 단계별 수렴 상태.
- 교차 검증 결과. 건너뛰었으면 그 사실과 사유.
- 시나리오 확인 결과와 backlog 건수.
- 다른 곳에서 쓰는 방법: `<이름>/` 디렉터리만 옮기면 된다. 스킬이 요구하는 전제 조건이 있으면 그것.
- 미수렴 단계나 미확인 사실이 남았으면 그것. 이 경우 완성됐다고 안내하지 않는다.

## 하지 말 것

- 스킬 없이 무엇이 잘못되는지 확인하지 않고 쓴다.
- description에 스킬의 절차를 요약해 넣는다(에이전트가 본문을 읽지 않고 요약만 따르게 된다).
- 이전 단계가 수렴하지 않았는데 다음 단계를 쓴다.
- 리뷰어나 상대 AI의 지적을 판정 없이 반영한다.
- 스킬 안에 `.makers/`, 절대 경로, 이 스킬(skill-maker)에 대한 참조를 남긴다.
- 스킬에 생성 과정의 기록(리뷰 기록, 수렴 상태)을 넣는다.
- 교차 검증을 건너뛰고도 수행한 것처럼 보고한다.
