# agent-maker

만들 에이전트에 대한 요구를 받아 **순차 정제**한 뒤 에이전트 정의 파일을 생성한다.

```
조사 → plans ─(수렴리뷰)→ spec ─(수렴리뷰)→ impl_plans ─(수렴리뷰)→ 에이전트 파일 생성 → 교차 검증·수정 → 확정
```

최종 목표는 이 대화를 모르는 호스트가 정의 파일만 받아, 맞는 작업을 그 에이전트에게 위임하고
에이전트가 지시문만으로 역할을 끝까지 수행하는 상태다.

## 원칙

- **역할 하나에 에이전트 하나.** 책임이 둘이면 둘로 나누거나 범위를 줄인다.
- **에이전트는 맥락 없이 시작한다.** 위임받은 에이전트는 부르는 쪽의 대화를 모른다.
  지시문만으로 무엇을 받고 무엇을 돌려줘야 하는지 알 수 있어야 한다.
- **권한은 최소로.** 역할에 필요한 도구·쓰기 권한만 준다.
- **중립 명세가 원본이다.** spec에서 호스트와 무관한 명세를 확정하고, 호스트별 파일은 거기서 옮겨 적는다.
  지시문 본문은 모든 호스트 파일에서 같다.
- **순차 생성, 불변 범위 계약.** 이전 단계가 수렴해야 다음 단계로 가고, plans의 범위 계약을 이후에 넓히지 않는다.
- **사용자가 멈추라고 하면 멈춘다.** 재개하면 그 단계의 수렴리뷰부터 잇는다.

## 절차

### 0. 스코프 확정

- `<이름>`(소문자·숫자·하이픈)과 역할 한 줄을 정한다.
- **대상 호스트**를 정한다. 기본은 Claude와 Codex 둘 다다. 사용자가 하나만 원하면 그것만 만든다.
- **출력 위치**를 정한다. 호출할 때 받았으면 그곳, 아니면 현재 프로젝트의 루트다.
  파일은 출력 위치 아래 호스트별 경로(agent-format §1)에 생성한다.
- 역할·위임 조건·기대 결과가 논의로 정해지지 않았으면 여기서 멈추고 사용자와 먼저 정한다.
- `.makers/agent/<이름>/`을 현재 작업 디렉터리에 만든다.

### 1. 조사

- 같은 역할의 에이전트가 이미 있는지 찾는다(출력 위치의 기존 정의, 호스트 기본 제공 에이전트).
  있으면 사용자에게 알리고 새로 만들지 정한다.
- 역할이 다룰 작업을 실제로 어떻게 하는지, 어떤 도구와 권한이 필요한지 확인한다.
- 이 에이전트에게 위임돼야 하는 작업 예시와, 위임되면 안 되는 비슷한 작업 예시를 모은다.

### 2. plans

`plans/00-<이름>-plan.md`를 agent-format §2의 필수 절로 쓴다. 범위 계약을 여기서 확정한다.
수렴리뷰 관점: 정합성·최소성·완결성.

### 3. spec

`spec/01-<이름>.md`에 호스트 중립 명세를 확정한다(agent-format §3).
수렴리뷰 관점: 정합성·최소성·완결성.

### 4. impl_plans

`impl_plans/01-<이름>.md`에 호스트별 정의 파일을 전문으로 쓴다(agent-format §4).
수렴리뷰 관점: 정합성·최소성·완결성·구현가능성. 호스트 파일이 둘 이상이면 교차정합을 더한다
(지시문 본문이 같은가, 권한이 같은 수준인가).

### 5. 에이전트 파일 생성

생성할 위치에 같은 것이 이미 있으면 먼저 artifact-layout §5에 따라 사용자에게 차이를 보이고 확인받는다.
impl_plans의 파일 전문을 출력 위치 아래에 그대로 만든다.

생성 후 독립성 관점으로 파일을 리뷰하고, artifact-layout §4의 기계 검사를 통과시킨다.
이어서 agent-format §5의 로드 확인을 수행한다. 확인하지 못한 호스트는 "미확인"으로 기록한다.

### 6. 교차 검증

cross-verification.md를 따른다. 대상은 생성된 정의 파일뿐이다.
상대 AI의 호스트용 파일을 만들었으면, 그 파일을 기준으로 "이 정의로 그 역할을 수행할 수 있는가"를 묻고
자기 호스트에서의 로드 확인(agent-format §5)도 요청한다.
상대 호스트용 파일을 만들지 않았으면(단일 호스트 출력), 생성된 파일의 위임 조건·지시문·입출력 계약을 읽고
"이 지시문만 받은 에이전트가 역할을 수행할 수 있는가"를 검토하게 한다. 이때 상대는 로드 확인을 하지 않으며,
보고에도 지시문 검토와 로드 확인을 구분해 적는다. 교차 검증 때문에 다른 호스트 파일을 추가로 만들지 않는다.
조건을 충족하지 못하면 건너뛰고 기록한다.
반영할 때는 spec의 중립 명세, impl_plans, 생성된 모든 호스트 파일을 함께 고쳐 서로 어긋나지 않게 하고,
기계 검사를 다시 통과시킨다.

### 7. 마무리

사용자에게 다음을 보고한다.

- 생성된 파일의 위치(호스트별), 단계별 수렴 상태.
- 교차 검증 결과. 건너뛰었으면 그 사실과 사유.
- 호스트별 로드 확인 결과. 확인하지 못한 호스트가 있으면 그 사실.
- backlog 건수.
- 다른 곳에서 쓰는 방법: 정의 파일을 대상 프로젝트의 같은 호스트별 경로에 옮긴다. 에이전트가 요구하는 전제 조건이 있으면 그것.
- 미수렴 단계나 미확인 사실이 남았으면 그것. 이 경우 완성됐다고 안내하지 않는다.

## 하지 말 것

- 위임 조건(description)을 모호하게 써서 호스트가 언제 맡겨야 할지 알 수 없게 한다.
- 지시문이 부르는 쪽의 대화 맥락을 전제한다.
- 역할에 필요 없는 권한을 준다.
- 호스트별 파일의 지시문을 서로 다르게 쓴다.
- 이전 단계가 수렴하지 않았는데 다음 단계를 쓴다.
- 리뷰어나 상대 AI의 지적을 판정 없이 반영한다.
- 정의 파일 안에 `.makers/`, 절대 경로, 이 스킬(agent-maker), 생성 과정의 기록을 남긴다.
- 로드를 확인하지 못한 호스트를 확인했다고 보고한다.
