# 에이전트 정의 형식과 단계별 문서

## 1. 호스트별 정의 파일

같은 중립 명세(§3)에서 호스트마다 파일 하나를 만든다. 경로는 출력 위치 기준이다.

### Claude — `.claude/agents/<이름>.md`

마크다운 파일. 프런트매터 뒤의 본문 전체가 에이전트의 지시문이다.

```markdown
---
name: <이름>
description: <위임 조건>
tools: <쉼표로 구분한 도구 이름>     # 선택. 생략하면 부르는 쪽의 도구를 모두 물려받는다
model: <모델>                        # 선택. 생략하면 호스트의 기본 선택 순서를 따른다
---

<지시문>
```

### Codex — `.codex/agents/<이름>.toml`

역할 하나당 TOML 파일 하나. 역할은 파일 이름이 아니라 `name` 값으로 식별된다.

```toml
name = "<이름>"
description = "<위임 조건>"
developer_instructions = """
<지시문>
"""
# 선택: model, model_reasoning_effort, sandbox_mode. 생략하면 호스트의 기본 선택 순서를 따른다.
```

필수 필드는 `name`, `description`, `developer_instructions`다.
쓰기가 필요 없는 역할은 `sandbox_mode = "read-only"`로 권한을 줄인다.

### 주의

- 위 형식은 각 호스트의 공식 문서를 기준으로 한다. 호스트 버전에 따라 달라질 수 있으므로,
  현재 호스트의 형식은 그 호스트의 문서나 도움말로 확인하고, 다르면 확인한 형식을 따르고 그 사실을 plans에 적는다.
- 프로젝트 범위의 정의는 호스트가 그 프로젝트를 신뢰할 때만 읽힐 수 있다.
- 모델을 생략했을 때 어떤 모델이 쓰이는지는 호스트마다 정해진 순서(호출할 때의 지정, 환경·설정의 기본값,
  부르는 쪽의 모델 등)를 따른다. 생략이 곧 "부르는 쪽과 같은 모델"을 뜻하지는 않는다.
  특정 모델이나 부르는 쪽과 같은 모델이 꼭 필요하면 그 호스트의 문서에서 지정 방법과 우선순위를 확인해 명시한다.
- 도구 이름과 권한 설정은 호스트마다 다르다. 중립 명세의 권한 수준을 각 호스트의 표현으로 옮긴다.
- 플러그인에 정의 파일을 넣는다고 자동으로 등록된다고 가정하지 않는다. 산출물은 위 경로의 파일이다.

## 2. plans — `plans/00-<이름>-plan.md`

[shared/artifact-layout.md](shared/artifact-layout.md) §3의 헤더로 시작하고 `END OF FILE`로 끝난다.
해당 없는 절은 지우지 않고 한 줄로 사유를 쓴다.

| # | 절 | 내용 |
|---|---|---|
| 1 | 문제와 완료 기준 | 이 에이전트가 맡을 역할과, 전담 에이전트가 없을 때의 문제. 완료 기준 목록 |
| 2 | 조사 결과 | 기존 유사 에이전트, 역할의 실제 수행 방법, 필요한 도구·권한, 대상 호스트의 형식 확인 결과 |
| 3 | 위임 시나리오 | 위임돼야 하는 작업 3개 이상, 위임되면 안 되는 비슷한 작업 2개 이상, 시나리오별 입력과 기대 결과 |
| 4 | 결정표 | D-ID · 결정 · 근거. 대상 호스트, 권한 수준, 모델 지정 여부, 출력 형식 등 |
| 5 | 범위 계약 | 에이전트가 하는 일 / 하지 않는 일 ([shared/triage.md](shared/triage.md) §1) |
| 6 | 검증 매트릭스 | 완료 기준 ↔ 확인 방법 1:1 |
| 7 | 리스크 | 남는 리스크와 수용 사유 |
| 8 | 미확인·이견 | 없으면 "없음" |

완료 기준에는 최소한 다음이 들어간다.

- 위임돼야 하는 작업에서 description만으로 이 에이전트가 선택된다.
- 지시문과 위임 입력만 받은 에이전트가 각 시나리오의 기대 결과를 돌려준다.

## 3. spec — `spec/01-<이름>.md` (호스트 중립 명세)

| 항목 | 내용 |
|---|---|
| 이름 | 소문자·숫자·하이픈. 모든 호스트 파일에서 같다 |
| 위임 조건 | 호스트가 언제 이 에이전트에게 맡기는지. 맡기면 안 되는 경우. 모든 호스트 파일의 description이 된다 |
| 입력 계약 | 부르는 쪽이 반드시 넘겨야 하는 것. 빠졌을 때 에이전트의 동작 |
| 지시문 | 역할, 절차, 판단 기준, 하지 말 것. 부르는 쪽의 대화를 모른다고 가정하고 쓴다 |
| 출력 계약 | 돌려주는 결과의 형식. 부르는 쪽은 이 결과만 본다 |
| 권한 수준 | 읽기 전용 / 작업 디렉터리 쓰기 / 그 이상. 필요한 도구 종류와 이유 |
| 모델 | 지정할 이유가 있을 때만. 없으면 "지정 없음(호스트 기본 선택)" |
| 전제 조건 | 에이전트가 필요로 하는 외부 도구·환경과 없을 때의 동작 |

이어서 호스트별 대응 표를 둔다. 권한 수준과 모델을 각 호스트에서 어떤 필드와 값으로 표현하는지 적는다.
근거가 된 plans의 결정(D-ID)과 미확인·이견을 적는다.

지시문은 특정 호스트의 도구 이름을 쓰지 않고 행위로 적는다. 그래야 모든 호스트 파일에 같은 본문을 쓸 수 있다.

## 4. impl_plans — `impl_plans/01-<이름>.md`

- 호스트마다 절 하나: 출력 위치 기준 상대 경로와 **파일 전문**.
- 호스트 파일 간 대조표: 이름·위임 조건·지시문 본문이 같은지, 권한이 같은 수준인지.
- 생성 순서와 생성 후 확인(§5).
- plans 검증 매트릭스의 완료 기준마다 확인 절차.
- 완료 체크리스트.

파일 전문은 그대로 복사해 쓸 수 있어야 한다. 자리표시자를 남기지 않는다.

## 5. 로드 확인

파일을 생성한 뒤 수행한다.

1. **형식 확인**: 마크다운 파일은 프런트매터가 올바른지, TOML 파일은 TOML로 읽히는지 확인한다.
2. **현재 호스트에서의 인식**: 현재 호스트가 사용할 수 있는 에이전트 목록에 새 에이전트가 나타나는지 확인한다.
   세션을 다시 시작해야 인식되는 호스트면, 그 사실을 사용자에게 알리고 "재시작 후 확인 필요"로 기록한다.
3. **시나리오 확인**: 인식되면 plans의 위임 시나리오 하나를 실제로 위임해 기대 결과와 비교한다.
4. **다른 호스트**: 현재 호스트에서 확인할 수 없는 호스트의 파일은 형식 확인까지만 하고 "미확인"으로 기록한다.
   그 호스트용 파일을 만들었고 교차 검증을 수행하면 상대 AI가 자기 호스트에서 확인한다.
   만들지 않은 호스트는 확인 대상이 아니다.

확인하지 못한 것을 확인했다고 적지 않는다.
기대 결과와 어긋나면 [shared/triage.md](shared/triage.md)로 판정해 반영한다.
