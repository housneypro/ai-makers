# goal 묶음 문서 형식

plans·spec·impl_plans 문서는 [shared/artifact-layout.md](shared/artifact-layout.md) §3의 헤더로 시작한다.
`goal.md`를 포함해 묶음의 모든 문서는 마지막 줄이 `END OF FILE`이다.
해당 없는 절은 지우지 않고 절 제목 아래 한 줄로 사유를 쓴다. 리뷰어가 누락과 구분할 수 있어야 한다.

## 1. plans — `plans/00-<이름>-plan.md`

| # | 절 | 내용 |
|---|---|---|
| 1 | 문제와 완료 기준 | 해결할 문제 한 문단, 직접 원인, 완료 기준 목록. 이후 모든 판정의 기준점이다. 완료 기준은 확인할 수 있는 문장으로 쓴다. |
| 2 | 조사 결과 | 대상(프로젝트 이름, 조사 시점 커밋 또는 자료 목록), 현재 흐름, 재사용 후보, 후보별 변경 규모 |
| 3 | 결정표 | 아래 열을 모두 채운다 |
| 4 | 대안 비교 | 결정표에 `신규`가 있을 때만. 없으면 "신규 도입 없음" 한 줄 |
| 5 | 범위 계약 | 포함 / 변경하지 않음 ([shared/triage.md](shared/triage.md) §1) |
| 6 | 단계 골격 | 실행 단계(P1…Pn)와 의존 관계. 단계를 나누는 근거는 의존 관계뿐이다 |
| 7 | 검증 매트릭스 | 완료 기준 ↔ 확인 방법 1:1. 여기 없는 검증은 impl_plans에도 없다 |
| 8 | 리스크 | 남는 리스크와 수용 사유 |
| 9 | 미확인·이견 | 확인하지 못한 사실과 이견. 없으면 "없음" |

결정표:

| 열 | 값 |
|---|---|
| D-ID | `D-01` … |
| 결정 | 무엇을 어떻게 |
| 재사용 판정 | `기존`(이미 있는 것으로 해결) \| `신규`(새로 도입) |
| 근거 | `기존`이면 재사용하는 것의 위치, `신규`이면 대안 비교의 행 |

`신규`는 대안 비교에서 다음 중 하나가 사실로 성립할 때만 채택한다.

- 기존 것으로 하면 바뀌는 범위가 신규보다 크다.
- 기존 것으로 하면 범위 계약의 "변경하지 않음"을 건드린다.
- 기존 것으로 하면 이미 쓰이는 곳이 깨지고, 신규는 그렇지 않다.
- 조사했지만 재사용할 수 있는 것이 없거나, 있는 것으로는 완료 기준을 충족할 수 없다.
  이 경우 대안 비교에 무엇을 어디서 찾아봤는지와 왜 쓸 수 없는지를 적는다.

"더 깔끔하다", "확장성이 좋다"는 근거가 아니다.

## 2. spec — `spec/01-<영역>.md` …

plans가 확정한 범위를 영역별로 상세히 적는다. 영역마다:

- 현재 상태: 대상의 실제 위치와 값(프로젝트 루트 기준 상대 경로).
- 바뀐 뒤의 상태: 정확한 값·이름·형식·동작. 실행자가 해석할 여지를 남기지 않는다.
- 경계 조건과 실패 시 동작.
- 근거가 된 plans의 결정(D-ID).
- 미확인·이견.

둘 이상의 영역이 공유하는 이름·값이 있으면 `spec/00-contracts.md`를 먼저 쓴다.

## 3. impl_plans — `impl_plans/01-<단위>.md` …

plans의 단계 골격(P1…Pn)마다 문서 하나를 둔다. 단계가 하나면 `01-<이름>.md` 하나로 끝낸다.
둘 이상이면 `00-overview.md`에 선결 조건·단계 의존 관계·최종 통합 검증·전체 완료 조건을 둔다.

단계 문서마다:

- 선결 조건: 이 단계 전에 끝나 있어야 하는 것. 사람이 해야 하는 일(권한·계정·외부 승인)은
  왜 필요한지, 정확한 절차, 완료 확인 방법까지 쓴다.
- 절차: 번호 붙인 단계. 정확한 명령(실행 위치 포함), 만들 파일의 내용, 바꿀 부분과 바뀐 뒤의 내용.
- 단계별 검증: 실행할 확인과 기대 결과. plans 검증 매트릭스의 완료 기준에 대응한다.
- 완료 체크리스트.
- 근거가 된 spec의 절.

## 4. goal.md

```markdown
# goal — <이름>

<목표 한 줄>

## 실행 방법
이 파일과 같은 디렉터리의 `plans/`·`spec/`·`impl_plans/`가 함께 있어야 한다.
대상 프로젝트의 루트에서 아래 단계를 순서대로 수행한다. 각 단계의 체크리스트와 검증을 통과하면
다시 지시를 기다리지 않고 다음 단계로 넘어간다. 마지막에 최종 검증과 완료 조건을 확인한 뒤에만 끝낸다.

## 실행 기준
- 대상: <프로젝트 이름> · 기준 커밋: <조사 시점 커밋, 없으면 "해당 없음">
- 수렴 상태: plans / spec / impl_plans
- 교차 검증: <PASS | 건너뜀 — 사유>

## 선결 조건
- [ ] <사람이 먼저 해야 하는 일. 없으면 "없음">

## 변경하지 않음
<범위 계약의 "변경하지 않음"을 옮긴다. 실행 중에도 지킨다.>

## 단계
### P1 <제목>
- 절차: [impl_plans/01-….md](impl_plans/01-….md)
- 체크리스트:
  - [ ] …
- 검증: <실행할 확인과 기대 결과>
- 다음 단계 진입 조건: …

## 최종 검증
- [ ] <plans 검증 매트릭스의 완료 기준마다 한 줄>

## 완료 조건
<모든 단계 체크리스트와 최종 검증이 통과한 상태를 한 문장으로>

## 막혔을 때
<실행자가 스스로 정하면 안 되는 것(범위 변경, 새 외부 효과)과 그때 멈추고 보고할 내용>

END OF FILE
```

`goal.md`는 묶음 안의 문서만 상대 경로로 가리킨다. `backlog.md`와 `cross-review/`는 언급하지 않는다.
대상이 기준 커밋 이후 바뀌어 절차와 어긋나면 실행자가 멈추고 보고하도록 "막혔을 때"에 적는다.
