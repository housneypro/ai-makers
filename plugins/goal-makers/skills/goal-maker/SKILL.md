# goal-maker

논의로 방향이 정해진 업무를 받아 **순차 정제**한다.

```
조사 → plans ─(수렴리뷰)→ spec ─(수렴리뷰)→ impl_plans ─(수렴리뷰)→ goal.md 생성 → 교차 검증·수정 → 확정
```

최종 목표는 이 대화를 모르는 실행자(다른 AI, 다른 사람)가 묶음만 받아 모든 단계를 완주할 수 있는 상태다.
산출물의 크기는 목표가 아니다. 완료 기준을 달성하는 데 필요한 것만 담는다.

## 원칙

- **조사가 결정보다 먼저다.** 대상을 보지 않고 경로·값·이름을 적지 않는다. 확인하지 못한 것은 "미확인"으로 적는다.
- **순차 생성.** 각 단계는 이전 단계 산출물을 근거로만 쓰고, 수렴해야 다음 단계로 간다.
- **범위 계약은 불변이다.** plans에서 확정한 "포함 / 변경하지 않음"을 이후 조사·리뷰가 뒤집지 않는다.
- **문서만 만든다.** 대상 프로젝트의 파일을 고치지 않는다. goal의 실행은 이 스킬의 일이 아니다.
- **사용자가 멈추라고 하면 멈춘다.** 재개하면 그 단계의 수렴리뷰부터 잇는다.
- **묻는 것은 사용자만 정할 수 있는 것으로 한정한다.** 조사로 알 수 있는 사실은 조사한다.

## 절차

### 0. 스코프 확정

- `<이름>`(소문자·하이픈)과 목표 한 줄을 정한다. 호출 인자가 있으면 그것을 쓴다.
- **대상 프로젝트**를 정한다. 호출 인자로 경로를 받으면 그곳, 없으면 현재 작업 디렉터리다.
  코드가 없는 업무(조사·기획·문서 작업)면 대상은 사용자가 준 자료다.
- 지금까지의 논의에서 확정된 방향·제약·값을 모은다. 방향이 정해지지 않았으면 여기서 멈추고
  사용자와 방향부터 정한다. 빈 논의에서 계획을 지어내지 않는다.
- `.makers/goal/<이름>/`을 현재 작업 디렉터리에 만든다. 같은 이름의 묶음이 이미 있으면 artifact-layout §5에 따라
  이어서 할지 새로 할지 사용자에게 묻고, 기존 `goal.md`를 바꾸게 되면 바꾸기 전에 차이를 보이고 확인받는다.

### 1. 조사

plans를 쓰기 전에 대상을 직접 조사한다. 결과는 plans의 조사 결과 절에 적는다.

- 문제가 지나는 현재 흐름과 직접 원인.
- 재사용 후보: 같은 문제를 이미 푸는 것, 기존 구조 안의 해법.
- 후보별 변경 규모(바뀌는 파일·영향 범위).
- 대상이 git 저장소면 조사 시점의 커밋. 나중에 대상이 바뀌었는지 판단하는 기준이다.

### 2. plans

`plans/00-<이름>-plan.md`를 goal-format §1의 필수 절로 쓴다. 범위 계약을 여기서 확정한다.
수렴리뷰 관점: 정합성·최소성·완결성.

### 3. spec

plans가 확정한 범위만 상세 명세로 쓴다(goal-format §2). 범위 계약 밖은 조사하지 않는다.
영역이 넓으면 artifact-layout §2에 따라 나눈다.
수렴리뷰 관점: 정합성·최소성·완결성. 나눠 썼으면 교차정합을 더한다.

### 4. impl_plans

plans와 spec을 근거로, 실행자가 그대로 따라 할 수 있는 절차를 쓴다(goal-format §3).
정확한 명령·바꿀 내용·단계별 검증·완료 체크리스트까지 적는다.
수렴리뷰 관점: 정합성·최소성·완결성·구현가능성. 나눠 썼으면 교차정합을 더한다.

### 5. goal.md 생성

`goal.md`를 goal-format §4의 형식으로 쓴다. 순서·게이트·완료 조건은 `goal.md`가 소유하고,
세부 절차는 같은 묶음의 impl_plans를 상대 경로로 가리킨다.

생성 직전에 대상이 조사 시점 이후 바뀌었는지 확인한다. 범위와 겹치는 변경이 있으면 해당 단계로 돌아간다.

생성 후 독립성 관점으로 묶음 전체를 한 번 리뷰하고, artifact-layout §4의 기계 검사를 통과시킨다.

### 6. 교차 검증

cross-verification.md를 따른다. 대상은 `plans/`·`spec/`·`impl_plans/`·`goal.md` 묶음 전체다.
조건을 충족하지 못하면 건너뛰고 기록한다.
반영으로 묶음이 바뀌었으면 기계 검사를 다시 통과시킨다.
결과가 정해지면 `goal.md`의 실행 기준에 교차 검증 결과를 적는다.

### 7. 마무리

사용자에게 다음을 보고한다.

- 묶음 위치와 단계별 수렴 상태.
- 교차 검증 결과. 건너뛰었으면 그 사실과 사유.
- backlog 건수.
- 묶음을 옮기는 방법: `.makers/goal/<이름>/`에서 `plans/`·`spec/`·`impl_plans/`·`goal.md`를 함께 옮긴다.
- 미수렴 단계나 미확인 사실이 남았으면 그것. 이 경우 실행 가능하다고 안내하지 않는다.

## 하지 말 것

- 조사 없이 결정표를 쓴다.
- 이전 단계가 수렴하지 않았는데 다음 단계를 쓴다.
- 리뷰어나 상대 AI의 지적을 판정 없이 반영한다.
- 범위 계약 밖 항목을 backlog가 아니라 본문에 넣는다.
- impl_plans를 "실행자가 알아서" 수준으로 쓴다.
- `goal.md`에 완료 체크리스트와 최종 검증이 없다.
- 묶음 밖(`backlog.md`, `cross-review/`, 절대 경로, 이 스킬)을 가리키는 참조를 남긴다.
- 교차 검증을 건너뛰고도 수행한 것처럼 보고한다.
