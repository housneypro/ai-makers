# 지침 파일 형식과 단계별 문서

## 1. 지침 파일

에이전트가 그 프로젝트에서 일할 때 세션마다 읽는 마크다운 문서다. 형식 제약은 없다.

**출력 파일**

- 기본은 대상 프로젝트 루트의 `AGENTS.md` 하나다. 여러 호스트가 함께 읽는 공용 파일이다.
- 대상 호스트가 `AGENTS.md`를 읽지 않고 자기 이름의 파일(예: Claude의 `CLAUDE.md`)만 읽으면,
  그 파일에는 규칙을 복사하지 않고 `AGENTS.md`를 가리키는 내용만 둔다. 규칙의 원본은 하나로 유지한다.
- 호스트가 어떤 파일을 읽는지, 다른 파일을 가리키는 방법이 무엇인지는 호스트 버전에 따라 다르다.
  그 호스트의 문서나 실제 동작으로 확인하고, 확인한 내용을 plans에 적는다.
- 하위 디렉터리에만 해당하는 규칙이 많으면 그 디렉터리에 지침 파일을 따로 둘 수 있다.
  호스트가 하위 디렉터리의 지침 파일을 읽는지 확인한 뒤에만 나눈다.
- 프로젝트에 이미 정해진 관례(예: "지침 파일은 하나만 둔다")가 있으면 그것을 따른다.

**좋은 규칙의 조건**

| 조건 | 뜻 |
|---|---|
| 근거가 있다 | 프로젝트에서 확인한 사실이거나 사용자가 정한 결정이다 |
| 읽어서는 알 수 없다 | 코드와 설정을 읽으면 알 수 있는 것은 적지 않는다. 이유·금지·순서·숨은 전제를 적는다 |
| 행동으로 옮길 수 있다 | 에이전트가 무엇을 하거나 하지 말아야 하는지 분명하다 |
| 지켰는지 확인할 수 있다 | 결과물을 보고 규칙 위반 여부를 가릴 수 있다 |
| 이유가 붙어 있다 | 자명하지 않은 규칙에는 이유를 한 구절로 적는다. 이유를 알아야 경계 사례에서 맞게 판단한다 |

**쓰는 방법**

- 호스트 중립적으로 쓴다. 특정 호스트의 도구 이름 대신 행위로 적는다.
- 명령은 그대로 실행할 수 있게 적고, 어디서 실행하는지도 적는다.
- 경로는 프로젝트 루트 기준 상대 경로다.
- 짧게 유지한다. 특정 작업에만 필요한 긴 절차는 지침 파일에 넣지 않고 별도 문서나 스킬로 빼고 가리킨다.
- 비밀값, 개인 환경에만 해당하는 내용, 곧 바뀔 임시 상태는 넣지 않는다.

**권장 구성** — 해당하는 것만 둔다.

1. 프로젝트가 무엇인지 한두 문장.
2. 구조: 읽어서는 알기 어려운 배치와 각 위치의 역할.
3. 명령: 빌드·테스트·실행·검사.
4. 규칙: 지켜야 하는 것과 하지 말아야 하는 것, 이유.
5. 완료 전 확인: 작업을 끝냈다고 하기 전에 통과시켜야 하는 것.

## 2. plans — `plans/00-<이름>-plan.md`

[shared/artifact-layout.md](shared/artifact-layout.md) §3의 헤더로 시작하고 `END OF FILE`로 끝난다.
해당 없는 절은 지우지 않고 한 줄로 사유를 쓴다.

| # | 절 | 내용 |
|---|---|---|
| 1 | 문제와 완료 기준 | 지침이 없거나 지금 지침으로는 에이전트가 무엇을 틀리는가. 완료 기준 목록 |
| 2 | 조사 결과 | 대상 프로젝트(이름, 조사 시점 커밋), 기존 지침 파일 목록과 요약, 확인한 명령과 실행 결과, 대상 호스트가 읽는 파일 확인 결과 |
| 3 | 규칙 후보 | R-ID · 규칙 요지 · 근거(프로젝트의 위치 또는 사용자 결정) · 출처(기존 지침 / 조사 / 사용자) |
| 4 | 확인 시나리오 | 지침을 읽은 에이전트에게 시킬 작업 3개 이상과, 규칙을 지켰을 때의 기대 결과 |
| 5 | 결정표 | D-ID · 결정 · 근거. 출력 파일 구성, 기존 규칙 처리 방침, 별도 문서로 뺄 것 등 |
| 6 | 범위 계약 | 지침이 다루는 것 / 다루지 않는 것 ([shared/triage.md](shared/triage.md) §1) |
| 7 | 검증 매트릭스 | 완료 기준 ↔ 확인 방법 1:1 |
| 8 | 리스크 | 남는 리스크와 수용 사유 |
| 9 | 미확인·이견 | 실행하지 못한 명령 포함. 없으면 "없음" |

완료 기준에는 최소한 다음이 들어간다.

- 지침에 적힌 모든 명령과 경로가 대상 프로젝트에서 실제로 맞다(있어야 하는 것은 있고, 금지한 것은 없다).
- 지침 파일과 프로젝트만 받은 에이전트가 확인 시나리오에서 규칙을 지킨 결과를 낸다.
- 기존 지침의 규칙 중 사용자가 바꾸라고 하지 않은 것은 뜻이 그대로다.

## 3. spec — `spec/01-<이름>.md`

- 출력 파일 목록과 각 파일의 역할.
- 절 구성.
- 규칙 목록: R-ID마다 **최종 문구**, 이유, 근거.
- 기존 지침이 있으면 대조표: 기존 규칙마다 유지·수정·삭제와 사유. 삭제와 수정은 사용자 결정이나 사실 오류가 근거여야 한다.
- 지침에 넣지 않고 별도 문서로 빼는 것과 그 위치.
- 근거가 된 plans의 결정(D-ID), 미확인·이견.

규칙 후보 중 §1의 "좋은 규칙의 조건"을 채우지 못하는 것은 여기서 뺀다. 뺀 것은 사유와 함께 적는다.

## 4. impl_plans — `impl_plans/01-<이름>.md`

- 출력 파일마다 절 하나: 대상 프로젝트 루트 기준 상대 경로와 **파일 전문**.
- 이미 있는 파일을 바꾸면 사용자에게 보일 대조표(유지·수정·삭제·추가).
- 생성 순서와 생성 후 확인(§5).
- plans 검증 매트릭스의 완료 기준마다 확인 절차.
- 완료 체크리스트.

파일 전문은 그대로 복사해 쓸 수 있어야 한다. 자리표시자를 남기지 않는다.

## 5. 사실 확인과 시나리오 확인

파일을 생성한 뒤 수행한다.

**사실 확인**

1. 지침에 적힌 경로를 규칙의 뜻에 맞게 확인한다. 있어야 한다고 적은 경로(읽을 파일, 실행 위치, 참고 문서)는
   존재하는지 본다. 만들지 말라고 한 경로는 없는지 본다. 앞으로 만들 위치나 예시로 든 경로는 존재를 요구하지 않는다.
2. 지침에 적힌 명령을 적힌 위치에서 실행해 동작을 확인한다.
   부작용이 있는 명령은 실행하지 않고 "미확인"으로 기록한다.

**시나리오 확인**

1. 독립 에이전트를 띄운다. 이 대화의 맥락과 `.makers/` 문서는 주지 않는다.
2. 대상 프로젝트 경로와 생성된 지침 파일, plans의 확인 시나리오 하나를 준다.
   프로젝트를 실제로 바꾸지 않도록 무엇을 어떻게 할지 계획만 답하게 하거나 사본에서 수행하게 한다.
3. 결과가 규칙을 지켰는지 기대 결과와 비교한다.
4. 확인 시나리오 각각에 대해 반복한다.

호스트가 독립 에이전트를 띄울 수 없으면 시나리오 확인을 건너뛰고 마무리 보고에 적는다.
어긋나면 [shared/triage.md](shared/triage.md)로 판정해 반영하고, 고친 부분에 해당하는 것만 다시 확인한다.
