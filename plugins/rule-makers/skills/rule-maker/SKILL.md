# rule-maker

대상 프로젝트를 조사하고 요구를 **순차 정제**한 뒤 지침 파일을 생성한다.

```
조사 → plans ─(수렴리뷰)→ spec ─(수렴리뷰)→ impl_plans ─(수렴리뷰)→ 지침 파일 생성 → 교차 검증·수정 → 확정
```

최종 목표는 이 대화를 모르는 에이전트가 지침 파일과 프로젝트만 받아, 그 프로젝트의 규칙대로 일하는 상태다.
지침 파일은 에이전트가 매 세션 읽는다. 길수록 비용이 들고 지켜질 확률이 떨어진다. 필요한 규칙만 담는다.

## 원칙

- **규칙마다 근거가 있다.** 프로젝트에서 확인한 사실이거나 사용자가 정한 결정이어야 한다. 일반론은 넣지 않는다.
- **프로젝트를 보면 알 수 있는 것은 적지 않는다.** 에이전트가 파일을 읽어 알 수 있는 구조·내용을 옮겨 적지 않는다.
  읽어도 알 수 없는 것(이유, 금지, 순서, 숨은 전제)을 적는다.
- **적은 사실은 직접 확인한다.** 명령은 실행해 보고, 경로는 존재를 확인한다.
- **기존 지침을 존중한다.** 이미 있는 규칙은 사용자가 바꾸라고 하지 않는 한 뜻을 바꾸지 않는다.
  이미 있는 파일은 사용자 확인 없이 덮어쓰지 않는다.
- **순차 생성, 불변 범위 계약.** 이전 단계가 수렴해야 다음 단계로 가고, plans의 범위 계약을 이후에 넓히지 않는다.
- **사용자가 멈추라고 하면 멈춘다.** 재개하면 그 단계의 수렴리뷰부터 잇는다.

## 절차

### 0. 스코프 확정

- `<이름>`(소문자·숫자·하이픈)과 목적 한 줄을 정한다. 이름은 작업을 구분하는 용도다(예: 프로젝트 이름).
- **대상 프로젝트**를 정한다. 호출 인자로 경로를 받으면 그곳, 없으면 현재 작업 디렉터리다.
- **대상 호스트와 출력 파일**을 정한다(rule-format §1). 기본은 대상 프로젝트 루트의 공용 지침 파일 하나다.
- 새로 만드는지, 이미 있는 파일을 고쳐 쓰는지 확인한다. 고쳐 쓰는 것이면 무엇이 문제여서 고치는지 사용자에게 듣는다.
- 담을 규칙의 방향이 정해지지 않았으면 여기서 멈추고 사용자와 먼저 정한다.
- `.makers/rule/<이름>/`을 현재 작업 디렉터리에 만든다.

### 1. 조사

- 기존 지침 파일을 모두 찾아 읽는다(루트와 하위 디렉터리, 호스트별 파일 포함).
- 프로젝트의 실제 구조, 빌드·테스트·실행 명령, 관례를 확인한다. 명령은 실행해 동작을 확인한다.
  실행하면 부작용이 있는 명령(배포, 데이터 변경)은 실행하지 않고 "미확인"으로 적는다.
- 에이전트가 이 프로젝트에서 실제로 틀렸거나 틀리기 쉬운 지점을 모은다(사용자의 경험, 이력, 코드의 함정).

### 2. plans

`plans/00-<이름>-plan.md`를 rule-format §2의 필수 절로 쓴다. 범위 계약을 여기서 확정한다.
수렴리뷰 관점: 정합성·최소성·완결성.

### 3. spec

`spec/01-<이름>.md`에 규칙의 최종 문구와 파일 구성을 확정한다(rule-format §3).
수렴리뷰 관점: 정합성·최소성·완결성.

### 4. impl_plans

`impl_plans/01-<이름>.md`에 생성할 파일을 전문으로 쓴다(rule-format §4).
이미 있는 파일을 고치는 것이면 기존 규칙별 처리(유지·수정·삭제)와 추가 규칙을 대조표로 함께 둔다.
수렴리뷰 관점: 정합성·최소성·완결성·구현가능성.

### 5. 지침 파일 생성

이미 있는 파일을 바꾸는 것이면 먼저 artifact-layout §5에 따라 사용자에게 변경 내용(대조표)을 보이고 확인받는다. 확인 없이 덮어쓰지 않는다.
확인받으면 impl_plans의 파일 전문을 출력 위치에 그대로 만든다.

생성 후 독립성 관점으로 파일을 리뷰하고, artifact-layout §4의 기계 검사를 통과시킨다.
이어서 rule-format §5의 사실 확인과 시나리오 확인을 수행한다.

### 6. 교차 검증

cross-verification.md를 따른다. 대상은 생성된 지침 파일이다. 상대 AI는 대상 프로젝트를 읽을 수 있다.
조건을 충족하지 못하면 건너뛰고 기록한다.
반영할 때는 impl_plans와 생성된 파일을 함께 고쳐 둘이 어긋나지 않게 하고, 기계 검사를 다시 통과시킨다.

### 7. 마무리

사용자에게 다음을 보고한다.

- 생성하거나 바꾼 파일의 위치, 단계별 수렴 상태.
- 기존 파일을 바꿨으면 유지·수정·삭제·추가한 규칙의 수.
- 교차 검증 결과. 건너뛰었으면 그 사실과 사유.
- 사실 확인과 시나리오 확인 결과. 실행하지 못해 미확인으로 남은 명령.
- backlog 건수.
- 미수렴 단계나 미확인 사실이 남았으면 그것. 이 경우 완성됐다고 안내하지 않는다.

## 하지 말 것

- 확인하지 않은 명령·경로를 지침에 적는다.
- "깨끗한 코드를 쓴다" 같은, 어느 프로젝트에나 해당하는 일반론을 넣는다.
- 프로젝트 구조나 파일 내용을 지침에 옮겨 적는다.
- 기존 규칙을 사용자 확인 없이 지우거나 뜻을 바꾼다.
- 같은 내용을 호스트별 파일에 따로따로 복사한다.
- 비밀값이나 개인 환경의 절대 경로를 넣는다.
- 지침 파일 안에 이번 작업의 중간 문서(`.makers/rule/<이름>/`)를 가리키는 참조나 생성 과정의 기록을 남긴다.
  (대상 프로젝트가 스스로 쓰는 경로·도구를 그 프로젝트의 규칙으로서 적는 것은 해당하지 않는다.)
- 이전 단계가 수렴하지 않았는데 다음 단계를 쓴다.
- 리뷰어나 상대 AI의 지적을 판정 없이 반영한다.
- 교차 검증을 건너뛰고도 수행한 것처럼 보고한다.
