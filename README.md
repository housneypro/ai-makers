# makers

Claude Code와 Codex 양쪽에서 설치할 수 있는 플러그인 마켓플레이스다.
"만드는 것을 만드는" 플러그인을 모은다. 각 플러그인은 계획을 단계별로 정제하고 리뷰로 수렴시킨 뒤
최종 산출물을 생성한다.

## 사용 방법

makers는 공장이다. 두 가지 방식으로 쓴다.

1. **생산소로 사용**: 이 저장소에서 산출물을 만든 뒤 원하는 프로젝트로 그대로 옮겨 쓴다.
   옮겨 간 프로젝트는 makers를 알 필요가 없다.
   goal과 rule은 대상 프로젝트를 조사해야 하므로, 호출할 때 대상 프로젝트 경로를 인자로 준다.
   인자가 없으면 현재 작업 디렉터리를 대상으로 본다.
2. **프로젝트에 설치해 사용**: 각 프로젝트에 makers 마켓플레이스를 설치하고 그 자리에서 산출물을 만들어 쓴다.

## 산출물 독립성

두 방식을 모두 지원하기 위해, 최종 산출물(goal·skill·agent·rule)은 makers 없이도 그대로 동작해야 한다.

- skill·agent·rule 산출물은 `.makers/`의 중간 문서(plans·spec·impl_plans·backlog·cross-review)를 참조하지 않는다.
  실행에 필요한 내용은 산출물 안에 모두 담는다.
- **goal은 예외다.** `goal.md`만 옮기지 않고 `plans/`·`spec/`·`impl_plans/`·`goal.md`를 한 묶음으로 옮긴다.
  이식 단위는 `.makers/goal/<이름>/` 디렉터리다. `goal.md`는 같은 묶음의 문서를 상대 경로로 참조할 수 있고,
  묶음 밖은 참조하지 않는다. `backlog.md`와 `cross-review/`는 묶음 안의 어떤 문서도 참조하지 않으므로
  함께 옮기지 않아도 된다.
- 산출물은 makers 플러그인·makers 저장소·Orca가 설치돼 있다고 전제하지 않는다.
- 금지하는 것은 이번 생성 작업에 대한 의존이다. 대상 프로젝트가 스스로 쓰는 경로·도구·정책을 설명하는 내용
  (예: 지침 파일이 그 프로젝트의 규칙으로서 `.makers/`를 언급하는 것)은 의존이 아니다.
- 산출물에 생성 당시의 절대 경로를 넣지 않는다. 산출물 내부 참조는 산출물 기준 상대 경로로,
  대상 프로젝트의 파일은 그 프로젝트 루트 기준 상대 경로로 적는다.
- 산출물이 여러 파일이면 한 디렉터리로 묶어, 그 디렉터리만 옮기면 되게 한다.
- 수렴리뷰와 교차 검증은 "산출물만 받았을 때 수행할 수 있는가"를 확인한다.
  교차 검증의 상대 AI에게는 이식 단위만 준다(skill·agent·rule은 산출물만, goal은 묶음 전체).

## 플러그인

| 플러그인 | 최종 산출물 |
|---|---|
| `goal-makers` | 해야 할 업무를 종합한 `goal.md` |
| `skill-makers` | 만들고자 하는 스킬(스킬 디렉터리) |
| `agent-makers` | 만들고자 하는 에이전트(에이전트 파일) |
| `rule-makers` | 프로젝트 지침 파일(`AGENTS.md` 등) |

## 공통 흐름

```
plan ─(수렴리뷰)→ spec ─(수렴리뷰)→ impl-plan ─(수렴리뷰)→ 산출물 생성 → 교차 검증·수정 → 산출물 확정
```

- 산출물(goal은 `goal.md`, skill은 스킬 디렉터리, agent는 에이전트 파일, rule은 지침 파일)은 impl-plan이 수렴한 뒤에 생성한다.
  교차 검증은 이렇게 생성된 산출물을 대상으로 하고, 지적을 반영해 고친 뒤에 확정한다.
  교차 검증을 건너뛰면 생성한 산출물을 그대로 확정한다.
- 각 단계는 이전 단계 산출물을 근거로만 작성하고, 수렴리뷰를 통과해야 다음 단계로 간다.
- 수렴리뷰는 관점별(정합성·최소성·완결성·구현가능성) 독립 리뷰어가 결함을 심각도와 함께 보고하고,
  작성자가 타당성을 판정해 반영하는 과정을 반복한다. 수렴 조건은 문서 결함 CRITICAL·HIGH 0건이다.
- 리뷰 항목은 문서 결함과 확장 제안으로 나눈다. 문서 결함은 사실 오류·모순·실행 불가·완료 기준에 필요한 누락,
  그리고 안전 결함(그대로 수행하면 데이터 손상·비밀 노출·승인되지 않은 외부 효과를 일으키는 것)이다.
  문서 결함은 반영하고, 확장 제안은 `backlog.md`에 격리한다.

## 교차 검증

상대 AI(Claude ↔ Codex)에게 "이 goal/skill/agent/rule을 네가 수행하는 데 문제가 없는가"를 묻는 단계다.

- **수행 조건**: Orca가 설치돼 있고 Orca 오케스트레이션 스킬(플러그인)도 설치돼 있을 때만 수행한다.
  교차 검증은 Orca 오케스트레이션으로만 한다.
  또한 현재 세션이 Orca 워커를 띄울 수 있어야 한다. maker 자신이 Orca 워커로 실행 중이면
  워커를 띄울 수 없으므로(조정자 터미널만 가능) 조건 미충족으로 본다.
- **조건 미충족 시**: 교차 검증을 건너뛴다. 건너뛴 사실은 결과 보고에 남긴다. 다른 대체 경로는 없다.
- **결과 적용**: 상대 AI의 검증 결과도 수렴리뷰와 같은 판정을 거친다. 타당성을 판단한 뒤
  문서 결함은 반영하고 확장 제안은 `backlog.md`에 등재한다. 상대의 지적을 무조건 반영하지 않는다.

## 리뷰 라운드 상한

단계별 수렴리뷰와 교차 검증에 똑같이 적용한다.

- 기본 상한은 3라운드다.
- 3라운드 안에 수렴하지 못하면 사용자에게 추가로 수행할 라운드 수를 묻는다. 이때 다음 두 가지를 안내한다.
  - 추가 횟수는 상한이다. 수렴하면 남은 횟수와 무관하게 즉시 끝낸다
    (예: 100회를 받아도 5회째에 수렴하면 5회에서 끝난다).
  - 추가 횟수를 받으면 라운드 카운트는 0부터 다시 센다.
- 추가 횟수도 다 쓰면 같은 방식으로 다시 묻는다.
- 다시 세는 것은 상한 판정용 카운트뿐이다. 리뷰 기록과 파일 이름의 라운드 번호는 처음부터 이어서 매긴다.

## 작업 산출물 — `.makers/`

중간 산출물은 작업 디렉터리의 `.makers/<종류>/<이름>/`에 둔다. git으로 추적한다.

- `<종류>`: `goal` | `skill` | `agent` | `rule`
- `<이름>`: 만들 대상의 이름(소문자·하이픈)

```
.makers/goal/<이름>/
  plans/00-<이름>-plan.md
  spec/01-<영역>.md …          공유 인터페이스가 있으면 00-contracts.md 먼저
  impl_plans/01-<phase>.md …   여러 phase면 00-overview.md 추가
  backlog.md                   미포함 판정 항목이 있을 때만
  cross-review/                교차 검증 요청·응답
  goal.md                      최종 산출물 (goal만 여기에 둔다)
```

스킬·에이전트·지침 파일의 최종 산출물은 `.makers/`가 아니라 출력 위치에 생성하고, `.makers/`에는 중간 문서만 남긴다.
출력 위치는 호출할 때 정한다. 정하지 않으면 현재 프로젝트에서 호스트가 스킬·에이전트·지침을 읽는 위치를 쓴다.
어느 종류든, 생성할 위치에 같은 파일이나 디렉터리가 이미 있으면 바꾸기 전에 사용자에게 차이를 보이고 확인받는다.
